# 手柄刷题脚本设计

- 日期：2026-09-24
- 状态：待评审
- 目标文件：`fenbi-gamepad.user.js`（新建，第 5 个脚本）
- 相关文件：`fenbi-memorize-layout.user.js`、`fenbi-ai-sidebar.user.js`

---

## 一、目标与边界

### 1.1 要解决的

躺床上用手柄刷粉笔背题页，不碰键鼠完成整个循环：**看题 → 选答案 → 看解析 → 翻下一题**，外加回退网页、交卷、开关 AI 助手面板。

成功的样子：

| | |
|---|---|
| 插上就能用 | 手柄连上、按一下任意键被识别，页面角标亮起显示手柄名 |
| 每个动作能自己绑 | 手柄型号不定，绑定界面里按一下手柄上的键就绑上 |
| 不干扰原来的 | 鼠标键盘照常用；手柄不抢焦点、不发合成键盘事件 |
| 不装另外两个脚本也能跑 | 选选项 / 翻题 / 滚动 / 交卷 / 回退走的都是粉笔原生 DOM |

### 1.2 明确不做

| 不做 | 为什么 |
|---|---|
| 填空题软键盘 | 用户明确排除。手柄打字要么做摇杆选字母的软键盘，要么上外接键盘，都是另一个项目 |
| 通用空间导航（任意网页） | 用户选定只做粉笔刷题场景。通用导航是另一套架构（焦点模型 + 元素可达性计算），不在这个脚本里 |
| 合成键盘事件 | 见 4.4。跟现有快捷键撞车，且谁先跑取决于监听顺序，出了 bug 极难查 |
| 每个动作的「装了 / 没装另外两个脚本」双路径 | 用户会三份全装（README 里「询问 AI」那条链路本来就要求装齐）。第二条路径是白写的。YAGNI |

> 「双路径」指的是**每条动作都写两套实现**。「当前第几题」的读取回退（2.2）不在此列 —— 那是一处约 20 行的查询，不是动作的执行路径。

## 二、架构

### 2.1 四层，以及那条分界线

一个文件里四层。**关键约束：①② 层不碰 DOM，③ 层不碰手柄。**

```
① 输入层   rAF 循环 → 读 buttons[].pressed / axes[]
           只在有手柄时跑；页面 hidden 时停
    ↓ 交出「这一帧按下了什么」——一个纯粹的按键标识集合
② 识别层   与上一帧 diff → 边沿事件
           按钮：按下沿触发一次
           按住：首次延迟 400ms，之后每 80ms 重复
           摇杆：死区 0.35，越过死区当方向键，共用同一套重复规则
    ↓ 交出「动作 id」
③ 动作层   ACTIONS 表：id → { 名字, 默认键, 可重复?, 执行() }
           执行时要么操作粉笔 DOM，要么 dispatch 事件给别人
④ 配置层   GM_getValue / GM_setValue 存「动作 id → 按键标识**列表**」
           按键标识 = 'button:0' | 'axis:1:-1'
```

**按键标识存成字符串**（`'button:0'`、`'axis:1:-1'`）而不是对象：GM 存储走 JSON，字符串比较和去重都省事，写进 DOM 属性、打进日志也都直接可读。

**一个动作绑的是一个列表，不是单个键。** 因为 3.1 的默认表里滚动同时给了十字键 ↑↓ 和左摇杆 —— 单值存不下。幸好解绑/重绑的界面代价很小。

**摇杆不做模拟量。** 死区之外一律当方向键，跟十字键共用边沿 + 长按重复那一套。做成「推得越远滚越快」需要一条独立的连续通路，会破坏「② 层全是纯函数」这条分界线，而躺着刷题用不上那个精细度。

**为什么这么切**：② 层全是纯函数（死区判定、边沿判定、重复计时、按键标识的序列化与比较）。这层最容易写错 —— 死区算错就是「摇杆一碰就飘」，重复计时算错就是「翻页翻飞」—— 而它不碰 DOM，所以能在 Node 里直接测，不用起 jsdom、不用等真定时器。③ 层不碰手柄，意味着测试里可以绕过整个输入链路直接调动作。

### 2.2 与另外两个脚本的契约

沿用仓库既有约定：**普通 `Event` + DOM 属性，不用 `CustomEvent.detail`**（README 第 422 行：跨沙箱传 detail 不稳，属性是两边都看得见的普通 DOM）。命名照 `fbai-ask` / `data-fbai-ask` 那套来。

#### 契约一：开关 AI 助手面板

现有 `fbai-ask` 是「递题目过去」，没有开关。新增一条：

| 名字 | 值 | 谁写 | 谁读 |
|---|---|---|---|
| `TOGGLE_EVENT` | `'fbai-toggle'` | 手柄脚本 dispatch | 侧边栏监听 |
| 结果属性 | `data-fbai-toggle-result` | 侧边栏写 | 手柄脚本读 |

握手照 `askAi()` 的样子：**擦掉旧结果 → dispatch → 读结果属性 → 清理**。结果码 `shown` / `hidden` / `none`（侧边栏没装）。读不到 `none` 之外的码就不做事，也不报错。

两侧的导出名：手柄脚本导出 `TOGGLE_EVENT`；侧边栏导出 `CONFIG.toggleEvent` 和 `CONFIG.toggleResultAttr`（照 `askEvent` / `askResultAttr` 现有的排法）。契约测试比对这两边。

改的是 `fenbi-ai-sidebar.user.js`，加一个监听 + 一个 `ui.toggle()` 调用 —— 它已经有 `ui.toggle()` 了（快捷键 `Ctrl+Alt+Q` 走的就是它）。

#### 契约二：当前在第几题

背题页是**一整条长列表**，不是一题一屏。布局脚本里的 `getCurrentQuestionIndex()` 已经在算这个：先按 DOM 标记找，找不到就取**离视口 35% 高度最近的那道题**，结果带 TTL 缓存。

布局脚本把结果写到 `documentElement` 上：

| 名字 | 值 | 谁写 | 谁读 |
|---|---|---|---|
| 当前题号属性 | `data-fbai-current-question` | 布局脚本 | 手柄脚本 |

手柄脚本读这个属性；**读不到就自己按同一套 35% 视口启发式算一遍**（约 20 行）。这样装不装布局脚本都能用。

两侧的导出名：布局脚本与手柄脚本各导出 `CURRENT_QUESTION_ATTR`，契约测试比对这两个值相等。

#### 但是：不要在每次动作前都跑这个启发式

35% 那条**只是兜底**，不该当唯一依据。手柄脚本自己维护一个 `trackedIndex`：

- **翻题**（十字键 ← →）→ `trackedIndex ± 1`
- **跳题**（答题卡浮层）→ 直接把选中的题号赋给它
- 这两条覆盖了绝大多数情况，而且**完全准确**，不依赖任何猜测

只有下面两种时刻才跑一次启发式来重置 `trackedIndex`：

1. 页面加载后的**首次**动作（还没有任何自己的记录）
2. **检测到不是自己引起的滚动** —— 用户用鼠标滚了，或者页面自己跳了。判据：`scroll` 事件防抖 200ms，且距离自己上次 `jumpToQuestion` 不足 600ms 的忽略掉

**为什么必须这样**：选错题的代价是**永久锁掉一道没做过的题**（6.1 答完即锁），不可撤销。而 35% 视口启发式在长题干、带图题、材料题上完全可能偏一道。让它当唯一依据太脆 —— 让它当兜底则刚好。

> ⚠️ **必须配一条契约测试**。照 `test/` 里那条 `assert.equal(layout.ASK_EVENT, sidebar.CONFIG.askEvent)` 的样子：两侧的名字对不上，表现是「按了没反应，页面上一点线索都没有」—— 正是最该被测死的一类。

### 2.3 界面

**设置浮层** —— GM 菜单一项「手柄设置…」开一个 shadow DOM 浮层，跟侧边栏同风格。内容：

- 顶部：检测到的手柄名 + `mapping` 是不是 `standard`
- 一张动作表：动作名 / 当前绑的键（**可能多个，每个键带一个「解除」**）/「重新绑定」
- 「重新绑定」→ 提示「按下手柄上的键」→ 抓下一个手柄输入 → **加进该动作的列表**；若这个键已经绑在别的动作上，先从那边摘掉（一个键不能同时干两件事）→ 存 → 立刻生效，不用刷新页面
- 全部恢复默认

**角标** —— 页面角落一个小标 `🎮 Xbox Wireless Controller`，没手柄时不显示。

角标不只是好看：**浏览器安全策略要求先按一下手柄上的键，`getGamepads()` 才会返回它**。插上不动等于没插。没这个提示，用户会以为脚本坏了。

### 2.4 文件与测试

| 文件 | 内容 |
|---|---|
| `fenbi-gamepad.user.js` | 单文件，形态与另外三个一致：IIFE + `module.exports` 出口，Node 里导出纯函数供测试，浏览器里 `init()` |
| `test/gamepad.test.mjs` | ② 层纯函数（死区、边沿、重复计时、按键标识序列化）+ ④ 层配置读写 |
| `test/gamepad-action.test.mjs` | 假手柄灌进 `navigator.getGamepads`，验「按下 → 第 3 题的 label 真的被 click 了」 |

## 三、交互设计

### 3.1 默认映射

8 个动作要塞进有限几个键，这是唯一的真矛盾。默认这么排 —— **全部可改**，这只是起点。

**关于按键称呼**：文档里一律用**标准映射的索引**（0–16）和方向（十字键 / 左摇杆 / LB / RB / LT / Start / Back），不用 A/B/X/Y。因为索引 0 是「下面那个键」，在 Xbox 上是 A、PS 上是 ×、Switch 上是 B —— 顺着手柄叫名字，换个手柄就全反了。这正是要自己映射的原因。

| 手柄 | 动作 | 说明 |
|---|---|---|
| 面键（索引 0 / 1 / 2 / 3） | **选项 1 / 2 / 3 / 4** | 直选。索引 0 是「下面那个键」，落在不同手柄上名字不同 |
| 十字键 → / ← | 下一题 / 上一题 | 长按连发 |
| 十字键 ↑ / ↓ | 上滚 / 下滚 | 长按连发，一步约视口 1/3 |
| 左摇杆 ↑ / ↓ | 上滚 / 下滚 | 走跟十字键**完全相同**的一套（见 2.1） |
| LB | 展开 / 收起解析 | |
| RB | 呼出答题卡跳题浮层 | 十字键选题号，面键 0 跳过去 |
| LT | 提交（多选题用） | 点 `.memorize-confirm-btn`，见 6.5。单选题用不上 |
| Start | 开关 AI 助手面板 | |
| **Back 短按** | 回退网页 | `history.back()` |
| **Back 长按 1 秒** | 呼出设置 / 按键帮助浮层 | 躺着忘了哪个键干什么，按它 |
| **Start 长按 1 秒** | 交卷 | 见 3.3 |

### 3.2 为什么「选项用四个面键直选」

备选是「摇杆移动高亮 + A 确认」：只占两个键、键位宽裕，但多一步操作，而且**必须在页面上画一个高亮框**，否则不知道选到哪了 —— 等于要多做一套视觉层。

躺着刷的场景下，直选明显更对：一看就知道按哪个，且不引入新 UI。代价是四个面键全占掉，别的动作往肩键 / 十字键 / Start / Back 上挤 —— 这正是 3.1 那张表的由来。

### 3.3 防误触是总原则

躺着的时候手柄容易压到，而**交卷不可逆** —— 误触一次整套练习就交了。所以：

- **所有动作走边沿触发**（按下那一刻响应一次），只有滚动和翻题这两个明确要连发的走长按重复
- **交卷 = 长按 1 秒 + 二次确认**，故意做得难按
- **`document.hidden` 时整个轮询停掉**，切到别的标签页就不响应
- **答完即锁，一题只有一次机会**（6.1 实测）。所以「面键直选」的误触代价是实的：随手一按，那道题就不能再用来自测了。这是**速度优先的自觉取舍** —— 选它是因为躺着刷题时少一步操作的价值更高。连带后果是 **`Back 长按` 呼出帮助浮层变得更重要**：看不懂键位乱按的代价，比坐在桌前时高

### 3.4 多选题的提交按钮（已实测）

`.memorize-confirm-btn`，文字「确定」。实测一道多选连点两个选项后：选中数 2、无解析、确认按钮出现且未禁用。

**3.1 里 LT 那条按原计划绑它，不再是占位。**

它的渲染条件是「**有选中项但未提交**」—— 提交后按钮消失、解析才出来（见 6.5）。所以 LT 的动作要写成「找得到就点，找不到就静默跳过」，不能写成「一进题就必须找到」。

### 3.5 震动反馈

**触发信号**：当前题的 `div.ti-container` 拿到 `correct` / `wrong` 类（6.6 实测 226ms 出现）。

| 判定 | 震动 | 参数 |
|---|---|---|
| 答对 | 短震**两下** | 各 100ms，中间隔 80ms，共 280ms |
| 答错 | 长震**一下** | 400ms |
| 上限 | — | **都控制在 0.5 秒以内** |

- **答对用两个马达的强弱差做出「两下」的区分度**：`weakMagnitude: 0.6` / `strongMagnitude: 1.0`。两下之间用 `setTimeout` 排，所以得**维护一个计时器 token**
- **新的震动取消上一次没震完的**：你答完立刻翻下一题时，上一题第二下还没响，不取消的话两个反馈会串在一起
- **翻题、跳题要取消还没触发的对错监听**：否则翻走之后原地响一下，莫名其妙
- **超时 3 秒放弃**：万一 `.ti-container` 没拿到类（比如那题其实是填空题），监听器不能永远挂着
- **`vibrationActuator` 是 Chrome / Edge 专属**，Firefox 和 Safari 上没有这个对象 —— 静默跳过，不报错
- **设置浮层里给一个开关**。震动虽无声，但不是所有人都想要

这个动作不占键位 —— 它是选选项/提交的副产品，不是独立动作。

## 四、错误处理与边界

1. **没手柄** → 轮询不启动，角标不显示，脚本静默。零开销。
2. **手柄断开**（`gamepaddisconnected`）→ 停轮询、撤角标、**清掉「按住中」的状态**。不清的话会卡在连发里一直翻页。
3. **粉笔改版、目标元素找不到** → 执行前探测，找不到就静默跳过 + `console.warn`，不弹窗不崩。跟仓库现有风格一致 —— README 里脱库那段就是「拦下来说一声，不装作成功」。
4. **不做合成键盘事件** → 一律直接操作 DOM。这是一条**约束**，不是实现细节：一旦开始发合成 keydown，就会跟 AI 面板的 `Ctrl+Alt+Q` 那类现有快捷键撞车，而且谁先跑取决于监听顺序，出了 bug 极难查。
5. **`mapping !== 'standard'` 的杂牌手柄** → 按键索引没有标准含义（标准映射下索引 0 是「下面那个键」：Xbox 是 A、PS 是 ×、Switch 是 B）。所以绑定界面必须**同时显示索引和原始值**让人按着试，并在浮层里明说「你这个手柄不是标准映射，默认键位可能是错的」。
6. **输入框聚焦时跳过选选项** → 页面上的自定义刷题数量输入框拿到焦点时，手柄按面键不该去选 A。因为不发键盘事件，打字本身没问题；但「选选项」这个动作要主动跳过。
7. **性能** → rAF 循环里只做数组读取和纯计算，**不查 DOM**。DOM 查询只在动作真正触发那一刻做。这是不掉帧的关键。

## 五、测试策略

### 5.1 那个坑

**jsdom 完全没有 Gamepad API** —— `navigator.getGamepads` 不存在，`gamepadconnected` 事件不存在。另外 `requestAnimationFrame` 要开 `pretendToBeVisual` 才有，而现有夹具没开。

所以测试脚手架要：

- 给 `navigator.getGamepads` 打桩，返回可控的假 `Gamepad` 对象（`{id, mapping, buttons:[{pressed,value}], axes:[]}`）
- 让 rAF 能被**手动步进**，而不是等真定时器 —— 等真定时器测试会飘

这两样收进 `test/harness.mjs` 里新增的 `bootGamepad()`，**不污染现有夹具**。现有 11 个测试文件都得继续能跑。

### 5.2 测什么

| 层 | 怎么测 |
|---|---|
| ② 识别层 | 纯函数直接喂帧序列。重点：死区边界（0.349 不触发 / 0.351 触发）、按下沿只触发一次、长按的 400ms/80ms 节奏、松开后状态清干净 |
| ④ 配置层 | 假 GM 存储读写往返；没存过时落回默认；坏数据（存了条不存在的动作 id）不炸 |
| ③ 动作层 | 起 jsdom，灌假手柄，步进 rAF，断言「按下面键 1 → 第 3 题的 `label.choice-radio-label` 收到 click」 |
| 震动 | 假 `vibrationActuator` 记录调用序列。重点：答对是两次 100ms、间隔 80ms；答错是一次 400ms；总时长都 ≤ 500ms；新震动取消上一次；翻题取消未触发的对错监听；超时 3 秒放弃；没有 `vibrationActuator` 时不炸 |
| 契约 | `gamepad.TOGGLE_EVENT === sidebar.CONFIG.toggleEvent`；`gamepad.CURRENT_QUESTION_ATTR === layout.CURRENT_QUESTION_ATTR` |

### 5.3 回归底线

现有 11 个测试文件全部保持通过。改动只碰 `fenbi-ai-sidebar.user.js` 的加信道那部分，所以重点盯 `test/panel.test.mjs` 和那条已有的信道契约测试。

## 六、已实测的页面事实

以下都是 2026-09-24 在真实背题页上跑探针测出来的，**不是从存档 HTML 推的** —— 存档那份是答完之后的快照，`input` 带 `disabled`，照它推会得出「这页只读」的错误结论。

### 6.1 点击选项是有效的

`label.click()` 确实能选中选项，**「选选项」这条通路成立**。时间线（单选，未作答的题）：

| 时刻 | 选项 class | 已选中 | 被禁用 | 有解析 |
|---|---|---|---|---|
| 点击前 | `input-radio` | false | false | false |
| 点击后·立即 | `input-radio` | **true** | false | false |
| 点击后·稍后 | `input-radio` | true | **true** | **true** |

三条结论：

1. **按下即有视觉反馈**（选项立刻变色）
2. **答完即锁**：`被禁用` 由 false 变 true，一题只能答一次。见 3.3
3. 解析的出现时机见 6.6 —— 早先一次粗采样曾误判成「约 1.5 秒」，那是采样粒度造成的假象，实测是 226ms 以内

### 6.2 三种题型的选项结构

| 题型 | 组件 | `ul` 类 | `li` 类 | `label` 类 | `input` 类 | 标记 `div` |
|---|---|---|---|---|---|---|
| 单选 | `app-choice-radio` | `choice-radios` | `choice-radio` | `choice-radio-label` | `option-radio` | `input-radio` |
| 多选 / 不定项 | `app-choice-checkbox` | `choice-checkboxs` | `choice-checkbox` | `choice-checkbox-label` | `option-checkbox` | `input-checkbox` |
| 判断 | `app-choice-true-false` | `choice-radios` | `choice-radio` | `choice-radio-label` | `option-radio` | `input-radio` |

两个坑：

- **`choice-checkboxs` 是粉笔自己的拼写错误**（应为 `checkboxes`）。实现时要照着错的写 —— 这种地方最容易被「顺手改对」，然后选择器静默失效。值得配一条断言钉死
- **判断题型不能靠 `app-ti` 的类来认**：实测一套 100 题的练习里所有 `app-ti` 都带 `question-multiple`，但选项组件混着三种。认题型要看里面挂的是哪个选项组件

### 6.3 `ul.allow` 就是「这题可作答」

- 可作答：`<ul class="choice-radios allow">`，input 不带 `disabled`
- 已锁：`<ul class="choice-radios">`，input 带 `disabled`

实测一套 100 题的练习：**52 道 `ul.allow`、48 道已有解析，两个数加起来正好 100**。

手柄输入该不该接受就认这个类 —— 比「猜有没有解析节点」可靠得多。

### 6.4 选项状态类

`correct`（正确答案）、`wrong`（选错了）、`true` / `false`（判断题）、`correctLost`。这些能看出一道题是不是已经摊开了。

### 6.5 多选题的确认按钮

`.memorize-confirm-btn`，文字「确定」。**渲染条件是「有选中项但未提交」**：选中选项后出现且可用，提交后消失、解析才出来。

### 6.6 对错信号，以及点击后的完整时间线

用 `MutationObserver` 监听整个 `body` 的 class / style 变化，点一个选项，实测时间线：

| 时刻 | 谁变了 | 变成什么 |
|---|---|---|
| +6ms | `div.fb-sol-panel` | `fb-sol-visible` |
| +24ms | `ul.choice-radios`、`input.option-radio` | Angular 的 touched/pristine |
| +225ms | `button.answer-btn`（原生答题卡） | `answer-btn wrong` |
| **+226ms** | **`div.ti-container`** | **`ti-container showBg wrong`** |
| +226ms | 原生解析区 `app-solution-choice` 整棵 | 带 `input-radio correct/wrong/correctLost`、`overall-item-value your-answer …`、`your-answer-wrong`、`correct-answer` |
| +393ms | `button.fbac-question`（布局脚本的答题卡） | `is-wrong` |

**`div.ti-container` 上的 `showBg` + `correct` / `wrong` 就是震动要的信号**，226ms 出现，对感知而言是即时的。

三条要点：

1. **这是纯 DOM 就够的信号，不需要任何新契约。** 一度考虑过「让布局脚本把接口里的答案写出来」（因为当时误以为要等 1.5 秒），现在作废 —— 不用改 `fenbi-memorize-layout.user.js`
2. **`correct` / `wrong` 是状态，`showBg` 只是「要不要画背景」的开关**（`.ti-container.wrong.showBg:before` 才上背景）。判对错认前两个，别认 `showBg`
3. **`div.ti-container` 在 `app-ti` 里面**，路径是 `app-ti > div.ti-container > div.ti-content`。这跟 6.2 的选项结构是分开的两层

`+225ms` 的 `.answer-btn` 和 `+393ms` 的 `.fbac-question` 是两个附赠信号 —— 后者可以给「答题卡跳题浮层」标出哪些题做对了、哪些做错了。

## 七、实施前还要验证的

原计划里的「多选提交按钮长什么样」和「选项能不能被 click」已由第六节实测解决。剩下两件：

1. **`trackedIndex` 与页面实际位置会不会失步**（2.2 末节）。自持索引把「选错题」的主要风险压掉了，但鼠标滚动那条重同步路径要实测：拿鼠标滚两下、再用手柄选，看选中的是不是屏幕上那道题。**失步的代价是永久锁掉一道没做过的题**（6.1 答完即锁），不可撤销
2. **多选题提交后，`.ti-container` 会不会也拿到 `correct` / `wrong`** —— 6.6 那条时间线是在**判断题**上测的。多选要先按 LT 提交才有结果，信号是否落在同一个地方没验过。不成立的话震动得多一条分支
3. **`fbai-toggle` 加进侧边栏后，原有快捷键不受影响** —— 侧边栏的 `Ctrl+Alt+Q` 走 `bindHotkey`，新信道是独立的 `document` 监听，理论上不冲突，但要有测试盯

## 八、实施顺序

1. ④ 配置层 + ② 识别层（纯函数，TDD，全程不碰 DOM）
2. ③ 动作层，先做「选选项 + 翻题」两条，在真实页面上验手感
3. **震动反馈**（3.5）—— 它是选选项的副产品，紧接着做，尽早拿真手柄验手感
4. 加角标 + 设置浮层（绑定界面）
5. 加契约：`fbai-toggle` 信道、`data-fbai-current-question` 属性
6. 补齐剩余动作：滚动、解析、跳题、交卷、回退
